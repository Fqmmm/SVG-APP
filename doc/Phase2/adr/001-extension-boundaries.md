# ADR 001：扩展契约与默认装配分离

状态：采用。

## 背景

Phase 1 的图形工厂和命令调度器分别维护固定类型表，序列化和格式化也枚举具体图形。添加一种图形时，往往要同时修改几个内核模块。

内置功能需要继续保留，同时还要允许插件增加命令、图形、属性处理和树标签。

## 决策

- 在内核定义 ShapeProvider、Command、AttributeHandler 和 TreeDecorator 四个扩展接口，每个 Framework 实例持有自己的注册表。
- 内置命令和图形实现在 `plugins/builtin/commands` 与 `plugins/builtin/shapes`，由 composition 创建并注册类实例。
- 插件通过 `extensions/index.ts` 使用公开接口、领域模型和编辑服务，调度器按注册结果调用具体实现。
- createEditor 将同一套注册表连接到命令和 SVG 读写；文件仓库的解析器与序列化器共用图形工厂。
- 默认构造入口集中在 `composition/defaults`。旧路径的纯转发文件已移除，内核目录中的文件统一接受依赖检查。
- 配置加载和激活失败回滚由宿主装配层负责，具体方案见 [ADR 004](004-plugin-loading.md)。

## 理由

注册表将“有哪些具体功能”交给装配代码决定。内核负责查找和调用，新增插件通过已有接口登记功能。

将默认装配集中起来，可以同时保留原有用法和可配置的插件组合。命令与文件读写共用注册表，避免 CLI 能创建一种图形、SVG 读写却不认识它。

注册表属于框架实例，可以让不同编辑器使用各自的插件组合，避免状态互相影响。

## 影响

- 内核不能引用具体插件或装配实现；插件不能绕过公开入口访问私有内核和装配模块。这两条规则由依赖检查验证。
- metrics 统计全部 CLI 源文件及转导出，区分内核、插件和装配，并生成分类行数与具名模块依赖图。
- 验证覆盖空框架、默认帮助、独立插件、四类重复注册和实例隔离；虚拟源码测试同时覆盖合法与违规依赖。
