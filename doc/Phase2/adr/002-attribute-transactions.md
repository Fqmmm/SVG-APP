# ADR 002：属性处理保持单次编辑事务

状态：采用。

## 背景

一次属性修改可能涉及多个子图形。例如修改复合容器时，处理器可能先改变一个部件，再改变另一个部件。

如果处理器各自写入历史，一次 set 会变成多个撤销步骤；如果修改到一半失败，文档还可能留下部分结果。因此，属性扩展需要统一的执行、撤销和失败恢复规则。

## 决策

- AttributeHandler 接收目标 Shape、属性名和值，通过公开图形方法修改目标或其后代。它不接收整个会话，也不直接操作历史、文档结构或画布。
- handles 只判断是否适用，不修改状态。apply 的修改范围限于目标子树中可由 captureState 恢复的状态。
- AttributeRouter 先收集全部匹配结果：没有匹配则使用原属性白名单；只有一个匹配则执行该处理器；多个匹配则报告 `ambiguous attribute handler`，不执行任何处理器。
- SetCommand 沿用 ShapeEditCommand 的前后快照。成功后只记录一个命令；undo 恢复修改前快照，redo 恢复修改后快照，不重新执行插件。
- 处理器抛错时恢复修改前快照，undo/redo 历史保持原状，包括已有的 redo 分支。失败后不再尝试默认属性规则。

## 理由

由统一的编辑命令管理历史，才能让用户的一次 set 始终对应一个撤销单元。保存修改后快照也使 redo 恢复原执行结果，不受插件再次运行时的状态影响。

多个处理器匹配时直接报错，可以明确暴露冲突，避免结果依赖加载顺序。处理器失败后立即回滚，避免默认规则掩盖插件错误或再次修改目标。

## 影响

- 即使一次 set 修改多个子部件，也只需要一次 undo 或 redo。
- 处理器不能通过外部闭包修改其他文档节点、文件或全局状态；这些副作用超出图形快照的恢复范围，插件作者需要自行管理。
- 事务支持属性状态恢复，文档结构变化和画布修改仍由相应的编辑机制处理。
- 验证覆盖多部件修改的一次撤销与重做、部分修改后抛错、失败后 redo 分支保留，以及多个处理器冲突时文档不变。
- 没有处理器时，普通 fill 仍可修改，未定义的 label 仍报错。
